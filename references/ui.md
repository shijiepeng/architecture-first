# 界面设计与 UI 修复

UI 问题可能来自父级约束或共享规则，单个截图变好也可能让其他页面变差。围绕使用问题定位责任与影响，确认边界沿用入口约定。新界面复用已确定的设计，建立够用的共享样式与组件；已有界面沿用项目的字体、颜色、间距、变体和断点规则，除非用户要求改变。

- **先定位负责问题的规则**：从组件及父级布局、样式来源和实际生效的样式入手；发现共享规则或影响超出局部时再扩大检查，不每次扫描全站。根据问题检查尺寸约束、对齐、溢出、定位、层叠与滚动容器；不要只找一个能覆盖现象的位置。
- **修正原始规则并收尾**：优先在负责该职责的组件或样式定义处修正，移除本次修正替代的重复或失效补丁。不要不断在文件末尾追加覆盖、提高选择器优先级、加负边距、固定尺寸或 `!important` 来压住根因。这些技术有合理用途，采用时应符合布局意图，而非掩盖尚未理解的问题。
- **明确影响范围**：修改共享组件、设计变量或全局选择器前，查明使用位置。属于通用规则的问题在共享层解决；只属于一个场景的差异用明确变体或局部作用域表达，不让局部修复污染全站，也不为每页复制一套相同规则。
- **让内容与布局共同成立**：考虑真实文字长度、数据量和目标窗口尺寸，不只对齐一张静态截图。保持页面层级、交互状态与滚动行为一致，不靠隐藏内容或无依据的截断掩盖溢出。
- **实际渲染验证**：通过浏览器或对应原生运行环境查看结果。按本次影响范围选择代表性的页面、窗口尺寸和状态；例如涉及宽度就看窄窗口和长内容，涉及弹窗就看遮挡、滚动、关闭和焦点，涉及共享组件就检查其他主要使用位置。无需穷举无关设备和状态组合。
- **保留有效证据**：用实际画面检查布局，必要时结合截图、计算样式和交互操作定位问题。编译通过、DOM 元素存在或截图已生成，都不能单独证明显示正确。无法实际预览时，明确尚未完成视觉验证，不声称显示问题已经解决。

局部修复保持局部目标；原布局无法承载需求时，说明根因和必要调整范围，重要未定取舍按入口确认。
