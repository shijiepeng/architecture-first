# 项目文档维护

仅在需要记录关键决定、改动使现有说明失效、保存阶段验收证据或用户要求整理文档时读取。先看相关文档的用途和已有约定，复用职责合适的位置；“少建文件”不等于把所有内容塞入 README。无文档影响的小修改无需新增文档或工作日志。

## 按用途安排内容

- **README**：供首次接触项目的人了解用途、快速启动、常用命令和文档入口。可保留简短的架构概览和关键使用限制；持续增长的架构细节、改造计划、逐日进展及测试日志移到合适的文档，以链接引导。
- **当前架构说明**：维护当前有效的职责、依赖、数据流、关键决定及现存限制。实现变化后原位更新对应内容，读者不应靠合并多天记录推断现状。
- **计划与决策历史**：确有长期价值时记录理由、取舍和状态。拟议、已确认待实施、已实现或已替代应可区分；已实施的方案同步到当前说明。沿用已有任务或决策记录，不为每次修改新增一套文件。
- **阶段审查与验收记录**：绑定版本、范围、环境和证据，追踪问题关闭或延期。可引用已有审查、CI 结果和测试报告，不重复抄录完整输出。后续复核注明新版本与结果，不能把历史失败记录改成好像当时就已通过。
- **使用、接口、测试与部署说明**：放实际操作步骤、必要条件和限制，随行为变化更新。短说明可留在已有文件，较长且有独立使用目的时再拆出；一次运行的临时路径、耗时或排查过程不自动成为长期操作说明。

这些是内容职责，不是必须创建的目录或文件清单。小项目可以只用 README；只有内容已经混杂、读者需要不同或维护频率明显不同时才拆分。尊重项目已有命名和组织方式，不设固定行数上限，不预建空文档或成套 GOALS、PLANS、ROADMAP、日志。

## 更新与整理

同一事实确定一个主要维护位置，其他位置使用必要的摘要与链接，避免复制整段后分别更新。迁出内容时同步更新 README 入口和受影响的链接，不保留两份独立演化的全文。

当前说明中的已解决问题及时更新；有价值的旧基线、决定理由和审查证据保留在历史记录中，并明确已被什么版本或决定替代。不把拟议方案当成已实现结构，不仅在文末追加“最新更新”而留下正文过时。

整理文档应保留仍有效的约束、未解决事项和验收证据，不能为了缩短篇幅静默删除。仅处理本次相关文档，不借局部修改重组整个文档体系。只读审查仍只提出建议，不擅自迁移文件。

完成后核对受影响的入口和本地链接，检查当前说明是否与实际实现一致、计划状态是否清楚、历史证据是否仍可定位。文档中引用的“测试通过”必须有相应证据；搬运旧记录不算重新执行测试。
