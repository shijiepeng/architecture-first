# 阶段独立审查与落地验收

## 触发与范围

当一个可验收的项目阶段、重大功能整体或交付版本即将宣告完成，必须进行详尽的独立审查与实际测试，不等用户说“现在要上线”才开始。普通改动沿用验证交付文件中的简短自查；聊天结束、一次提交或改动行数本身不定义阶段。根据已有计划、可独立验收的业务能力或用户指定的里程碑识别阶段，不为每个小改动另造里程碑。

沿用已确定的阶段目标和真实落地场景，核对实现与累计集成结果。阶段可限定功能范围，生产交付必须满足完整上线条件；核心能力未接通不能以“后续再补”宣告阶段完成。用户明确要求的原型按原型目标验收，清楚标注其与生产要求的差距，不擅自将需要落地的项目降格为原型。

先记录可复核的审查对象：版本或提交、工作区未提交及未跟踪的相关文件、阶段起点和累计改动范围、目标环境、验收依据。不能只审最后一次提交，或用仅比较 HEAD 的命令漏掉实际交付文件。没有 Git 时记录文件范围和快照。复用已有需求、对话中确认的决定和项目文档；不以缺少规格文件为由跳过需求审查，也不要求用户重写已知需求。

## 复用已有审查与测试

先查看已有 Codex 审查报告、其他独立评审及 CI/测试记录，核对它们实际覆盖的版本或文件快照、比较基线、任务范围、审查要求、执行者及完成状态；运行证据还要核对环境、依赖和配置。复用可追溯且仍适用的证据，不因进入本技能再启动一轮同范围通用审查或重跑同一检查。仅打开 diff、具备审查功能或推测已自动审查，不算完成证据。

不要按工具名称固定划分“Codex 查 bug、本技能查架构”。Codex 的实际审查也可能覆盖需求、架构、安全或专项问题；按该次任务要求和报告判断覆盖范围。“没有发现问题”可作为已声明范围内的审查结果，不代表所有维度均已检查，也不要求报告逐行证明看过每段代码。

已有独立审查可满足其覆盖范围内的独立性要求。若已覆盖阶段累计改动、整体需求和跨模块集成，就不再安排同职责审查者；若只检查本次 diff 的缺陷，则补查尚未覆盖的阶段需求、集成和交付条件。对下表维度只需在已有记录中标明已覆盖、需补查或不适用，避免再建一套重复报告。补查前说明尚缺的具体问题；为核实另一个未覆盖的行为而读取同一文件，不等于重复审查。

借鉴 PR Review Toolkit 的测试质量、静默失败、类型约束、注释准确性和代码简化视角，按适用性与覆盖缺口选用；不固定启动六名代理，不叠加其通用 code-reviewer 与已有同范围审查，不把 code-simplifier 当作验收必需的重构步骤。

## 独立审查如何开展

实现者容易沿用设计时的假设；独立审查用于重新核对需求、调用关系和运行证据，发现自查时未提出的问题。

独立审查由未承担该阶段实现的审查者或新上下文子代理执行，已完成且符合上述条件的 Codex 审查也可计入。整体需求与跨模块集成必须获得独立审查；只有现有证据未覆盖时才新增对应审查任务。按缺口、规模和风险分配专项，分工覆盖完整范围，避免多人重复扫描。提供任务目标、已确认及有依据的隐含要求、项目约定、审查对象、入口、测试证据和已知环境限制；不要把实现者的推理历史或“已经正确”的结论当成审查依据。

审查者直接读取代码、相关调用方、配置和部署文件，自行核实关键行为及测试证据。审查保持目标源码、索引和分支只读；需要运行程序、测试或生成产物时使用安全的测试环境或隔离副本，不能改动生产数据。审查者不递归派生审查者、不边审边重构。实现者负责核实发现、修复及回归。

独立执行条件不具备时，说明缺少的独立审查及可继续完成的测试工作；可以先自查推进，但不得将同一实现者换一种提示词的自查标为独立审查，不得声称强制验收已通过。

## 审查维度

以下维度帮助发现遗漏，不规定审查顺序、代理数量或实现方法。逐一判断适用性与已有证据，只深入检查未覆盖或失效的部分。适用项需要覆盖依据，不适用项可简述原因；检查恢复能力不意味着所有项目都要建队列、监控平台或额外防御分支。

| 维度 | 要检查的实际问题 |
|---|---|
| 需求与使用流程 | 明示目标、已确认取舍和合理隐含要求是否完成；跨页面/接口/后台任务的完整流程是否通畅；是否只有按钮、目录或接口外壳；是否越界增加能力。对可能影响方案的需求歧义单独提出，不能擅自假定用户接受。 |
| 正确性与集成 | 调用方、接口与实际数据是否一致；配置从保存到加载再到执行是否真正生效；类型或 schema 是否在需要的边界生效；外部服务、模型提示词、任务状态与结果是否真实接通；是否存在只在模拟条件下成立的实现。 |
| 架构与复杂度 | 职责、依赖方向、规则权威来源是否清楚；修改是否到处同步；是否存在不必要的转发层、猜测性扩展、重复配置或失效补丁。解释具体维护代价，不把文件数量、设计模式、类型数量当质量指标。 |
| 数据、类型与状态 | 类型、schema 与运行时约束是否表达并守住业务不变量（如字段之间的关系、合法状态转换），外部输入是否在实际边界得到校验；不为简单数据强加类层级或重复校验。业务需要的事务、一致性、并发与重复请求处理是否成立；进程重启或多实例下状态是否可靠；数据库约束和迁移是否兼容已有数据；涉及持久化时核实保存、读取和恢复路径。 |
| 权限与敏感数据 | 按实际边界检查身份与权限、用户/租户隔离、对象访问、外部输入、密钥和日志暴露；涉及文件或外部地址时检查对应入口。没有相关能力时不发明认证体系，也不能因用户未逐项要求而遗漏必要保护。 |
| 错误与恢复 | 可实际遇到的超时、取消、断连、部分失败如何呈现和恢复；重试是否有界、是否重复副作用；错误是否被吞掉；回退是否悄悄替换业务规则、伪造成功或产生不可信结果。 |
| UI 与交互 | 在实际运行画面中检查主流程、共享组件、适用的窗口尺寸与内容长度、空/加载/错误状态、操作反馈及必要的键盘与焦点行为；编译通过和截图生成不算视觉验收。无 UI 项目不执行此项。 |
| 测试质量 | 测试是否验证用户行为、模块边界及重要失败路径，是否会因真实缺陷而失败；关键集成是否被模拟遮蔽；测试预期是否独立于实现；是否为了变绿而削弱断言或跳过失败。覆盖率数字不替代有效性；测试应允许不改变行为的重构，不为简单取值或实现细节堆断言。 |
| 注释与说明 | 关键注释、接口约定、示例及运行说明是否与实际行为一致，是否误导调用、维护或部署；解释必要的原因与限制，不要求为显而易见的代码增加注释。 |
| 运行与部署 | 实际构建、生产启动命令、运行时版本、环境变量、依赖及资源是否齐备；干净环境是否能按说明启动；真实数据库和外部服务是否可用；迁移、权限、文件存储及任务执行是否适配部署环境。开发模式能跑不等于部署成功。 |
| 运维、性能与恢复 | 按预期使用规模检查代表性负载、慢请求、资源限制及模型调用成本；关键失败是否可发现和定位；适用时验证备份恢复、升级与回滚或不可逆迁移的恢复方案。小项目可采用简单日志和启动检查，不默认建设监控平台或分布式系统。 |

区分本次引入的问题与既有问题；既有缺陷若阻断当前阶段或上线，同样需要列为阻断项，不能只因不在 diff 中忽略。与本阶段无关的技术债单独记录，不借审查全面重写。

## 必须实际执行的验证

按验收条件核实实际执行的检查，记录环境、版本、命令或操作、结果与必要证据。同一交付对象在适用环境下已完成的 CI 或其他测试日志可直接计入，不要求在本地重复执行；缺少或失效的验证必须补跑。代码审查、阅读测试代码与实际运行测试是不同证据，互不替代；CI 单元测试也不能代替缺失的真实集成或部署验证。适用的关键验证不能用静态阅读或模型推断代替：

- 确认项目已有且适用的构建、类型/静态检查和自动化测试已实际通过；按缺口补充关键回归，不为指标增加无意义测试。缺少某种工具时采用实际适用的验证，不为凑流程安装整套工具链。
- 在安全测试环境跑通核心端到端用户流程，包括真实持久化与关键依赖。模拟可以验证逻辑，但不能代替对真实服务协议、配置和鉴权的集成验证。AI 功能用代表性输入检查提示词/工具/检索链路及输出可用性；根据业务风险检验质量、延迟和成本，不能以 HTTP 成功作为完成证据。
- 运行与项目相关的重要失败/恢复用例及 UI 验证；涉及并发、迁移或重启持久化的改动，执行对应测试。涉及既有数据的迁移使用测试数据或安全副本验证，不能直接拿生产数据试错。
- 准备上线时，必须在目标环境或已说明差异的生产相似环境完成构建、启动、必要迁移和冒烟验证；部署后在已有授权范围内检查真实服务主流程。审查通过不自动授权发布、合并、发送消息、产生新费用或操作生产数据。

缺少凭证、环境或外部依赖时，先完成能做的审查与测试，明确未验证项、影响和最小补齐条件。不得以临时假数据、跳过测试或修改预期掩盖阻断。必要的集成或部署证据缺失时，只能报告“待验证”，不能宣布可上线。

## 发现、修复与复核

合并不同审查来源中根因、触发条件和影响相同的发现，保留来源与修复状态，不把重复发现当成多个问题。每条发现包含：具体位置或路径、触发条件、实际后果、代码或运行证据、严重程度及必要的修复方向。明确区分已确认缺陷、待验证怀疑和可选建议；模型自报置信分数不等于证据。不设问题数量配额，允许没有值得修改的问题；不以个人写法偏好要求改代码。

- **阻断**：核心需求缺失、关键流程失败、安全/数据严重风险、无法在目标环境运行，或证明关键交付条件所必需的验证缺失。修复并复测后才能通过对应阶段或上线验收。
- **重要**：有具体影响的集成、恢复、维护或测试缺口。默认在阶段结束前解决；若不影响本阶段承诺，可在说明影响后由用户明确同意延期，不能由实现者默认为可接受。
- **建议**：不影响验收的改进，可记录后续处理，不为清空建议制造新抽象。

先核实发现，再在授权范围内修复；与需求或重要方案有关的未定取舍按入口规则确认。保留问题状态及修复证据。修复后重跑受影响测试和必要回归，并交由独立审查者复核阻断/重要问题及修复的关联影响。版本、依赖、配置或环境变化导致证据失效时，按影响范围更新对应证据，不使无关的已通过检查全部失效；仅在新改动、新失败或未解决风险需要时扩大检查，不无限重复完整审查。

## 验收结论

在项目已有验收记录中更新，或缺少时保留一份简洁记录，写明：审查对象与阶段、独立审查者和覆盖范围、已执行验证及结果、缺口和不适用项、问题关闭情况及用户同意的延期。按 [文档维护](documentation.md) 选择记录位置，保留版本对应的历史证据，不把每轮验收追加到 README，也不复制一份已有 CI 或审查报告。

分别回答“本阶段是否达到目标”和“是否具备目标环境上线条件”。只有独立审查已完成、适用的必要测试通过、阻断项关闭且重要问题已处理或获得明确延期同意时，才可宣布对应验收通过。明确限定证据覆盖的环境与范围；审查无发现不保证无缺陷，通过阶段验收不自动代表生产部署已验证。

不得把失败测试、未接通的关键集成或上线阻断只列入“后续建议”，然后宣布完成。没有足够证据就说明未通过及剩余工作，不以“代码写完”“能编译”“页面看起来正常”替代落地交付。

## 借鉴来源

以下是组织方式的参考，规则已按本技能的范围、确认原则和落地目标重新综合，不要求安装这些项目：

- [Matt Pocock code-review](https://github.com/mattpocock/skills/blob/main/skills/engineering/code-review/SKILL.md)：分开检查需求实现与工程规范。
- [Superpowers code-reviewer](https://github.com/obra/superpowers/blob/main/skills/requesting-code-review/code-reviewer.md)：独立上下文、实际用户预期、证据与分级反馈。
- [Anthropic PR Review Toolkit](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/pr-review-toolkit)：借鉴测试行为、静默失败、类型不变量、注释准确性和复杂度检查，按缺口使用。
- [Codex Code Review](https://learn.chatgpt.com/docs/code-review?surface=app)：审查可带具体任务与项目规则；复用实际完成的审查，查看差异本身不算执行审查。
