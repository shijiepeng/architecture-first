# UI Design and Repairs

UI problems may originate in parent constraints or shared rules. Improving one screenshot can worsen other pages. Locate responsibility and impact around the user-facing problem, following the entrypoint's confirmation boundaries. For new UI, reuse established designs and build sufficient shared styles and components. For existing UI, retain the project's typography, colors, spacing, variants, and breakpoint rules unless the user requests a change.

- **Locate the rule responsible for the issue first**: start with the component, parent layout, style sources, and computed styles. Expand when you find shared rules or impact beyond the local area; do not scan the entire site each time. Check relevant size constraints, alignment, overflow, positioning, stacking, and scroll containers. Do not merely find a place where an override hides the symptom.
- **Correct the original rule and clean up**: prefer fixing the component or style definition that owns the responsibility. Remove duplicate or obsolete patches superseded by this correction. Do not keep appending overrides, increasing selector specificity, or adding negative margins, fixed sizes, or `!important` to suppress the root cause. These techniques have legitimate uses, but should serve the intended layout rather than conceal an unexplained problem.
- **Make the impact explicit**: before changing shared components, design variables, or global selectors, identify where they are used. Solve general rule problems in the shared layer. Express scenario-specific differences with explicit variants or local scope. Do not let a local fix affect the whole site or duplicate identical rules for every page.
- **Make content and layout work together**: account for real text lengths, data volumes, and target window sizes, rather than matching one static screenshot. Keep page hierarchy, interaction states, and scrolling behavior consistent. Do not hide content or truncate it without justification to conceal overflow.
- **Verify actual rendering**: view the result in a browser or the relevant native runtime. Choose representative pages, window sizes, and states based on the change's impact. For width changes, inspect narrow windows and long content; for dialogs, inspect occlusion, scrolling, dismissal, and focus; for shared components, inspect other main usage locations. There is no need to enumerate unrelated device and state combinations.
- **Retain useful evidence**: inspect layout in the actual rendered view, using screenshots, computed styles, and interaction checks where helpful to diagnose issues. A successful build, a DOM element's presence, or a generated screenshot alone does not prove correct display. If an actual preview is unavailable, explicitly state that visual verification remains incomplete; do not claim the display issue is resolved.

Keep local fixes focused on local goals. If the original layout cannot support the requirement, explain the root cause and necessary adjustment scope. Follow entrypoint confirmation rules for significant unresolved tradeoffs.
