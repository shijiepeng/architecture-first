# Independent Stage Review and Deployment Acceptance

## Trigger and Scope

Before declaring an independently acceptable project stage, a major feature as a whole, or a delivery version complete, conduct thorough independent review and actual testing. Do not wait for the user to say “we are going live.” Ordinary changes use the brief self-check in verification and delivery. The end of a chat, a commit, or the number of changed lines does not define a stage. Identify stages from existing plans, independently acceptable business capabilities, or user-specified milestones; do not invent a milestone for every small change.

Use the established stage goals and real deployment scenario to check the implementation and cumulative integration results. A stage may limit functional scope, but production delivery must satisfy all release conditions. Do not declare a stage complete with “we will add it later” when core capabilities are disconnected. Evaluate an explicitly requested prototype against its prototype goals and clearly identify its gap from production requirements. Do not downgrade a project intended for actual use into a prototype on your own.

First record a review target that others can verify: version or commit, relevant uncommitted and untracked workspace files, the stage's starting point and cumulative change scope, target environment, and acceptance criteria. Do not review only the last commit or use commands comparing only HEAD that omit actual deliverable files. Without Git, record the file scope and snapshot. Reuse existing requirements, decisions confirmed in conversation, and project documentation. Do not skip requirements review because a specification file is missing or ask the user to rewrite known requirements.

## Reuse Existing Reviews and Tests

First inspect existing Codex review reports, other independent reviews, and CI/test records. Check the versions or file snapshots they actually cover, comparison baseline, task scope, review requirements, reviewer, and completion status. For execution evidence, also check the environment, dependencies, and configuration. Reuse traceable, still-applicable evidence. Do not launch another generic review or rerun the same checks merely because this skill has been invoked. Opening a diff, having review functionality available, or assuming an automatic review occurred is not evidence of completion.

Do not divide responsibilities rigidly by tool name, such as “Codex checks bugs; this skill checks architecture.” A Codex review may cover requirements, architecture, security, or specialized concerns; determine coverage from the actual task and report. “No issues found” may be a valid review result within its declared scope. It does not imply that every dimension was checked, nor must a report prove line by line that every piece of code was read.

An existing independent review can satisfy independence requirements within its coverage. If it already covers cumulative stage changes, overall requirements, and cross-module integration, do not assign another reviewer the same responsibility. If it checks only defects in the current diff, add review of uncovered stage requirements, integration, and delivery conditions. For the dimensions below, simply mark existing records as covered, needing additional review, or not applicable; avoid another duplicate report. Explain the specific remaining questions before adding review. Reading the same file to verify a different uncovered behavior does not constitute duplicate review.

Draw on PR Review Toolkit perspectives on test quality, silent failures, type constraints, comment accuracy, and code simplification according to applicability and coverage gaps. Do not automatically start six agents, duplicate its generic code-reviewer with an existing review of the same scope, or make code-simplifier a mandatory refactoring step for acceptance.

## Conducting an Independent Review

Implementers tend to retain assumptions from design. Independent review rechecks requirements, calling relationships, and execution evidence to find questions that self-review did not raise.

Use a reviewer who did not implement the stage or a subagent with a fresh context. A completed Codex review that meets the conditions above may also count. Overall requirements and cross-module integration must receive independent review; add a corresponding review task only when existing evidence does not cover them. Assign specialties according to gaps, scale, and risk, ensuring full coverage without multiple reviewers rescanning everything. Provide task goals, confirmed and supported implicit requirements, project conventions, the review target, entrypoints, test evidence, and known environmental limitations. Do not supply the implementer's reasoning history or a conclusion that the work is “already correct” as review evidence.

Reviewers directly read the code, relevant callers, configuration, and deployment files, and independently verify key behavior and test evidence. Keep target source files, the index, and branches read-only during review. If running programs, tests, or generating artifacts is necessary, use a safe test environment or isolated copy and never modify production data. Reviewers do not recursively spawn reviewers or refactor while reviewing. The implementer verifies findings, makes fixes, and runs regressions.

If independent execution is unavailable, explain the missing independent review and the tests that can still be completed. Self-review may move the work forward, but the same implementer checking their work under a different prompt must not be labeled independent review, and mandatory acceptance must not be claimed to have passed.

## Review Dimensions

These dimensions help identify omissions; they do not prescribe review order, agent count, or implementation methods. Assess applicability and existing evidence for each, then examine only uncovered or invalidated areas in depth. Applicable items need a basis for coverage; briefly explain why others do not apply. Checking recoverability does not mean every project needs queues, a monitoring platform, or extra defensive branches.

| Dimension | Actual questions to examine |
|---|---|
| Requirements and user workflows | Are explicit goals, confirmed tradeoffs, and reasonable implicit requirements fulfilled? Do complete workflows across pages, APIs, and background jobs work? Are there only buttons, directories, or interface shells? Were capabilities added outside scope? Raise ambiguities that could affect the solution separately; do not silently assume user acceptance. |
| Correctness and integration | Are callers, interfaces, and actual data consistent? Does configuration take effect from saving to loading to execution? Do types or schemas apply at the necessary boundaries? Are external services, model prompts, task states, and results actually connected? Does any implementation work only under mocked conditions? |
| Architecture and complexity | Are responsibilities, dependency direction, and authoritative sources of rules clear? Must changes be synchronized everywhere? Are there unnecessary forwarding layers, speculative extensions, duplicate configuration, or obsolete patches? Explain concrete maintenance costs rather than using file counts, design patterns, or type counts as quality metrics. |
| Data, types, and state | Do types, schemas, and runtime constraints express and enforce business invariants, such as relationships among fields and valid state transitions? Is external input validated at actual boundaries? Avoid imposing class hierarchies or duplicate validation on simple data. Do required transactions, consistency, concurrency, and duplicate-request handling work? Is state reliable across process restarts or multiple instances? Are database constraints and migrations compatible with existing data? Where persistence is involved, verify saving, reading, and recovery paths. |
| Permissions and sensitive data | Check identity, authorization, user/tenant isolation, object access, external input, secrets, and log exposure at actual boundaries. Check relevant entrypoints for files or external addresses. Do not invent an authentication system when the capability is absent, but do not omit necessary protections merely because the user did not list them individually. |
| Errors and recovery | How are realistically encountered timeouts, cancellations, disconnects, and partial failures presented and recovered from? Are retries bounded, and can they duplicate side effects? Are errors swallowed? Do fallbacks silently replace business rules, fabricate success, or produce untrustworthy results? |
| UI and interaction | In the actual running interface, check the main workflow, shared components, applicable window sizes and content lengths, empty/loading/error states, action feedback, and necessary keyboard and focus behavior. Successful compilation and screenshot generation do not count as visual acceptance. Skip this dimension for projects without UI. |
| Test quality | Do tests verify user behavior, module boundaries, and important failure paths, and would they fail on real defects? Do mocks hide key integrations? Are expectations independent of the implementation? Were assertions weakened or failures skipped just to turn tests green? Coverage numbers do not replace effectiveness. Tests should allow behavior-preserving refactoring and should not accumulate assertions for simple getters or implementation details. |
| Comments and guidance | Are key comments, interface contracts, examples, and operating instructions consistent with actual behavior, or do they mislead callers, maintainers, or deployment? Explain necessary reasons and limitations without requiring comments for self-evident code. |
| Runtime and deployment | Are the actual build, production startup command, runtime versions, environment variables, dependencies, and resources complete? Can a clean environment start from the instructions? Are real databases and external services available? Do migrations, permissions, file storage, and job execution fit the deployment environment? Running in development mode does not equal successful deployment. |
| Operations, performance, and recovery | Check representative load, slow requests, resource limits, and model-call costs against expected usage scale. Can key failures be detected and diagnosed? Where applicable, verify backup restoration, upgrades and rollbacks, or recovery plans for irreversible migrations. Small projects may use simple logs and startup checks; do not default to building monitoring platforms or distributed systems. |

Distinguish newly introduced issues from pre-existing ones. A pre-existing defect that blocks the current stage or release is still a blocker; do not ignore it merely because it is outside the diff. Record unrelated technical debt separately and do not use review as an opportunity for a comprehensive rewrite.

## Verification That Must Actually Run

Check actual executions against acceptance criteria and record the environment, version, command or action, result, and necessary evidence. Completed CI or other test logs for the same deliverable in an applicable environment can count directly without rerunning locally. Missing or invalidated verification must be run. Code review, reading test code, and actually running tests are distinct forms of evidence and cannot replace one another. CI unit tests cannot replace missing real integration or deployment verification. Applicable critical checks cannot be replaced by static reading or model inference:

- Confirm that the project's existing applicable build, type/static checks, and automated tests have actually passed. Add key regressions to fill gaps rather than meaningless tests for metrics. If a tool is absent, use verification that genuinely fits; do not install an entire toolchain merely to complete a process.
- Run core end-to-end user workflows in a safe test environment, including real persistence and critical dependencies. Mocks can verify logic but cannot replace integration checks of real service protocols, configuration, and authentication. For AI features, use representative inputs to check prompt/tool/retrieval paths and output usability. Evaluate quality, latency, and cost according to business risk; an HTTP success is not completion evidence.
- Execute important project-relevant failure/recovery cases and UI checks. For changes involving concurrency, migrations, or persistence across restarts, run corresponding tests. Verify migrations involving existing data with test data or safe copies; do not experiment directly on production data.
- Before release, complete the build, startup, necessary migrations, and smoke checks in the target environment or a production-like environment with documented differences. After deployment, check the actual service's main workflow within existing authorization. Passing review does not automatically authorize publishing, merging, sending messages, incurring new costs, or operating on production data.

If credentials, environments, or external dependencies are missing, first complete available review and testing, then specify unverified items, their impact, and the minimum conditions needed to resolve them. Do not hide blockers with temporary fake data, skipped tests, or altered expectations. Missing necessary integration or deployment evidence means “pending verification,” not ready for release.

## Findings, Fixes, and Rechecks

Merge findings from different sources when they share the same root cause, trigger, and impact. Preserve their sources and fix status; do not count duplicates as separate problems. Each finding includes a specific location or path, triggering conditions, actual consequences, code or runtime evidence, severity, and necessary direction for a fix. Clearly distinguish confirmed defects, suspicions needing verification, and optional suggestions. A model's self-reported confidence score is not evidence. Do not impose finding quotas; having no issues worth changing is acceptable. Do not require code changes based on personal style preferences.

- **Blocking**: missing core requirements, failed critical workflows, serious security/data risks, inability to run in the target environment, or missing verification necessary to demonstrate a critical delivery condition. Fix and retest before passing the corresponding stage or release acceptance.
- **Important**: integration, recovery, maintenance, or testing gaps with concrete impact. Resolve by stage completion by default. If the gap does not affect the stage's commitments, the user may explicitly agree to defer after its impact is explained. The implementer cannot assume it is acceptable.
- **Suggestion**: an improvement that does not affect acceptance. Record it for later if useful; do not create new abstractions just to clear suggestions.

Verify findings first, then fix them within authorization. Follow entrypoint confirmation rules for unresolved tradeoffs involving requirements or significant designs. Retain issue status and fix evidence. After fixing, rerun affected tests and necessary regressions, and have an independent reviewer recheck blocking/important findings and related effects of the fix. When version, dependency, configuration, or environment changes invalidate evidence, update affected evidence without invalidating unrelated passed checks. Broaden checks only when new changes, failures, or unresolved risks require it; do not repeat comprehensive review indefinitely.

## Acceptance Conclusions

Update the project's existing acceptance record, or keep one concise record if none exists. Identify the review target and stage, independent reviewer and coverage, executed checks and results, gaps and inapplicable items, issue closure, and deferrals agreed to by the user. Follow [Documentation maintenance](documentation.md) to choose the location and preserve version-specific historical evidence. Do not append every acceptance cycle to the README or duplicate an existing CI or review report.

Answer separately: “Has this stage met its goals?” and “Is it ready for release in the target environment?” Declare the corresponding acceptance passed only when independent review is complete, necessary applicable tests have passed, blockers are closed, and important findings are resolved or explicitly approved for deferral. State the environment and scope covered by the evidence. A review with no findings does not guarantee no defects, and stage acceptance does not automatically mean production deployment has been verified.

Do not list failing tests, disconnected critical integrations, or release blockers merely as “future suggestions” and then declare completion. Without sufficient evidence, state that acceptance has not passed and explain remaining work. “Code is written,” “it compiles,” or “the page looks normal” cannot substitute for delivery that works in its intended environment.

## Sources of Inspiration

The following informed the organization. The rules have been synthesized for this skill's scope, confirmation principles, and delivery goals; installing these projects is not required:

- [Matt Pocock code-review](https://github.com/mattpocock/skills/blob/main/skills/engineering/code-review/SKILL.md): examine requirement fulfillment separately from engineering standards.
- [Superpowers code-reviewer](https://github.com/obra/superpowers/blob/main/skills/requesting-code-review/code-reviewer.md): independent context, actual user expectations, evidence, and graded feedback.
- [Anthropic PR Review Toolkit](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/pr-review-toolkit): test behavior, silent failures, type invariants, comment accuracy, and complexity checks, applied according to gaps.
- [Codex Code Review](https://learn.chatgpt.com/docs/code-review?surface=app): reviews may include specific tasks and project rules. Reuse reviews actually completed; viewing a diff alone is not performing a review.
